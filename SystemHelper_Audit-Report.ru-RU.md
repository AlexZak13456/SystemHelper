# Глава 1 — Краткое изложение

## 1.1 Вывод в одном предложении

Это **компонент управления устройствами, предустановленный на аппараты, кастомизированные для China Unicom**. Без ведома пользователя, без возможности отказаться и без возможности отключить он периодически собирает данные обоих слотов SIM (IMEI, IMSI, ICCID, номер телефона), данные о базовых станциях и полный список установленных приложений с временем использования и трафиком, и выгружает их на сервер оператора. **Канал выгрузки может быть переписан любым обычным приложением на устройстве, перенаправив данные третьей стороне.**

## 1.2 Три уровня

**Уровень первый — что делает приложение (конфиденциальность)**

Одна запись из 39 полей содержит IMEI, IMSI, ICCID и номер телефона обоих слотов, идентификатор соты и код зоны местоположения, состояние VoLTE/5G, публичный IP, объём ОЗУ и накопителя, а также по **каждому установленному приложению** — имя пакета, отображаемое имя, время работы в foreground и трафик по каждому слоту. Базовые данные выгружаются раз в 24 часа, инвентарь приложений — раз в 7 дней, первая скрытая выгрузка происходит через 4 минуты после загрузки.

**Уровень второй — насколько он хрупок (безопасность)**

Сервис `RegisterHelperService`, несущий эту логику, объявлен с `exported="true"`, но **без `android:permission`**. Его Binder-метод `a(String)` напрямую записывает адрес сервера выгрузки. Одного подключения любого приложения достаточно, чтобы перенаправить все последующие данные — без разрешений, без root, без действий пользователя.

**Уровень третий — законно ли это (право)**

Ни одно из шести законных оснований не выполняется. Полнота раскрытия — 23%, и текст никогда не отображался. Все четыре элемента согласия не выполняются. Ноль из десяти законных прав реализовано. Это гражданско-правовое нарушение; административное нарушение весьма вероятно; уголовная ответственность имеющимися доказательствами не подтверждается.

## 2.4 Достаточно ли поиска по строкам

Жёсткое ограничение формата DEX делает поиск по именам классов **полным** для вопроса «вызывается ли данный API»:

> Любой вызов метода должен быть зарегистрирован в `method_ids`, а `method_ids` ссылается на имена классов и методов в `string_ids`. **Следовательно, если код вызывает `MediaProjectionManager`, `SurfaceControl.screenshot` или рефлексивно использует строку `"android.view.SurfaceControl"`, эта строка обязательно присутствует в `classes.dex`.**

Единственные три способа обойти это ограничение проверены и пусты:

| Способ обхода | Проверка | Результат |
|---|---|---|
| Динамическая загрузка dex | `DexClassLoader` / `PathClassLoader` / `InMemoryDexClassLoader` / `dalvik/system` / плагин-фреймворки | **Везде ноль** |
| Реализация в native | количество `.so`, `loadLibrary` | **0 файлов .so, 0 вызовов** |
| Команды с сервера | Без локальной реализации неисполнимы | Не применимо |

Дополнительно: `Class.forName` встречается ровно один раз и загружает `SystemProperties` и различные `TelephonyManager` (`ColorOSTelephonyManager`, `HwTelephonyManager`, `MzTelephonyManager`, `MSimTelephonyManager`, `TelephonyManagerEx`, `DmUnicomAbsTelephonyManager`) — **ни одного класса, связанного с дисплеем или графикой**.

## 2.5 Ограничения (4)

1. **Динамический анализ не проводился.** Ни реального устройства, ни эмулятора; трафик не перехватывался. Все выводы основаны на статической декомпиляции.

# Глава 3 — Профиль приложения

## 3.1 Что это за ПО

**Компонент управления устройствами (DM, Device Management) для аппаратов, кастомизированных под China Unicom.**

Пять независимых линий доказательств:

| № | Доказательство | Уровень |
|---|---|---|
| 1 | Домен выгрузки `dm.wo.com.cn:18080` («wo» — потребительский бренд Unicom), эндпоинт `/registerv3` | `[A]` |
| 2 | Зашитые значения MCC/MNC Unicom `46001 / 46006 / 46009` как критерий «сеть Unicom» | `[A]` |
| 3 | **Сертификат в `assets/pub.cer` имеет субъект `C=CN, ST=BJ, L=BJ, O=UNICOM, OU=UNICOM, CN=UNICOM`** — ключ шифрования выпущен от имени China Unicom | `[A]` |
| 4 | Встроенная таблица соответствия 200+ моделей и 50+ производителей | `[A]` |
| 5 | Платформенная подпись (`O=BBK, OU=IQOO`) + `sharedUserId` + предустановка | `[A]` |

Пункт 3 — самое твёрдое документальное доказательство: это не вывод из доменного имени, а прямое указание в открытом ключе, используемом для шифрования.

## 3.4 Подпись и корень доверия

```
Субъект       : EMAILADDRESS=bbktel@bbktel.com, CN=bbkmobile.com.cn,
                OU=IQOO, O=BBK, L=Dongguan View, ST=Guangdong, C=CN
Серийный номер: b153730d8a352539
Срок действия : 2012-09-25 → 2040-02-11 (28 лет)
Алгоритм      : SHA1withRSA / 2048 бит
Расширения    : BasicConstraints CA:true (PathLen без ограничений)
SHA-256       : BC:C3:5D:...:4F:0C:02
```

Три проблемы:

1. **Ключ подписи является ключом CA** (`CA:true`). Повторное использование ключа подписи приложения как ключа CA — антипаттерн управления ключами; радиус поражения выходит далеко за пределы одного приложения.
2. **Платформенный ключ широко распространён.** Данные субъекта совпадают с публично циркулирующим платформенным ключом vivo/BBK, который многократно перепаковывался в сторонних прошивках.
3. **Срок 28 лет** — намного больше любого разумного цикла ротации.

> Примечание: APK содержит блок подписи v2/v3 (`APK Sig Block 42` присутствует), поэтому классическая атака Janus (CVE-2017-13156) **неприменима**.

## 3.5 Открытый ключ выгрузки

```
Файл          : assets/pub.cer (X.509 в DER)
Субъект       : C=CN, ST=BJ, L=BJ, O=UNICOM, OU=UNICOM, CN=UNICOM
Алгоритм подписи: sha256WithRSAEncryption
Срок действия : 2019-05-24 → 2119-04-30 (**100 лет**)
Открытый ключ : **RSA 1024 бита**
```

**RSA 1024 бита более не считается стойким** (NIST SP 800-57 с 2013 года не рекомендует его для новых систем, PCI DSS прямо запрещает), а **ротация раз в 100 лет** означает, что при утечке закрытого ключа период поражения — целый век. Это же объясняет, почему подпись занимает 128 байт, а не 256.

# Глава 4 — Какие данные собираются

## 4.1 39 выгружаемых полей

Модель данных `com.mobiletools.systemhelper.control.c` содержит 40 полей-членов; **39 сериализуются в JSON выгрузки** (40-е — внутренний кэш):

| Категория | Поля | Что можно установить или вывести |
|---|---|---|
| **Устройство (7)** | `Manuf`, `Model`, `HWVersion`, `SWVersion`, `OS`, `OSVersion`, `DeviceType` | Модель, партия, версия прошивки, кастомизирован ли аппарат |
| **SIM 1 (10)** | `IMEI1`, `ICCID1`, `IMSI1`, `MSISDN1`, `MNC1`, `NCLS1`, `CellID1`, `LAC1`, `VolteEnabled1`, `5GEnabled1` | Идентификатор устройства + идентификатор SIM + номер телефона + местоположение + настройки радиосвязи |
| **SIM 2 (10)** | `IMEI2`, `ICCID2`, `IMSI2`, `MSISDN2`, `MNC2`, `NCLS2`, `CellID2`, `LAC2`, `VolteEnabled2`, `5GEnabled2` | То же; владельца двух SIM можно связать с двумя личностями |
| **Сеть (6)** | `AccType`, `IPv4`, `IPv6`, `DataSlot`, `SignalInfo`, `SubType` | Тип доступа, публичный IP, слот данных по умолчанию; **`SubType` фактически `{RAM, ROM, FREE}`**; **`SignalInfo` содержит RSRP/SINR/RSRQ + cellid + LAC + время + координаты** |
| **Инвентарь приложений (1 массив)** | `AppInfo[]`: `appLabel`, `pkgName`, `runTime`, `tx1`, `rx1`, `tx2`, `rx2`, `totalData1`, `totalData2`, `totalDataWiFi` | Что установлено, сколько используется, сколько трафика расходует каждое |
| **Метаданные (5)** | `RegType`, `SpecVersion`, `RegVersion`, `Time`, `History[]` | Тип триггера, версия, время, история |

## 4.2 Это не «информация об устройстве», это информация о человеке

Из 39 полей только 7 описывают само устройство — **18%**.

Остальные 32 (**82%**) описывают:

- **Человека, который его держит** — номер телефона, идентификатор SIM (IMSI/ICCID)
- **Где этот человек находится** — идентификатор соты и код зоны, публичный IP, опционально координаты GPS
- **Что этот человек делает** — какие приложения установлены, сколько каждое используется, сколько трафика расходует на каком слоте

Называть этот набор «информацией об устройстве» — самая существенная подмена понятий в этом отчёте.

## 4.3 Оценка чувствительности

По статье 28 Закона КНР о защите персональных данных (PIPL) — чувствительная информация это данные, утечка или неправомерное использование которых способна причинить вред достоинству личности либо угрозу личной или имущественной безопасности:

| Поле | Чувствительно? | Основание |
|---|---|---|
| `IMEI1/2` | **Да (конкретная личность)** | Уникальный идентификатор устройства, связываемый с абонентской базой |
| `IMSI1/2`, `ICCID1/2` | **Да (конкретная личность)** | Уникальные идентификаторы SIM, напрямую привязанные к владельцу договора |
| `MSISDN1/2` | **Да (конкретная личность)** | Номер телефона — носитель регистрации по реальному имени |
| `CellID1/2` + `LAC1/2` | **Да (траектория перемещений)** | Позиционирование на уровне соты; вместе с History восстанавливается маршрут |
| `SignalInfo.location` | **Да (траектория перемещений)** | Координаты GPS в открытом виде |
| `AppInfo[]` | **Да (выводится религия / здоровье / финансы)** | После агрегирования раскрывает несколько категорий из статьи 28 |

**Вывод: 13 полей являются чувствительной персональной информацией по закону** (12 по обоим слотам + `SignalInfo.location`), **плюс одна категория — инвентарь приложений, — из которой чувствительная информация выводится.**

## 4.4 Время и частота

| Триггер | Интервал | Содержимое | Код |
|---|---|---|---|
| Загрузка | **задержка 4 минуты** | Базовые данные | `OnBootReceiver` + `b(ctx, 240000L)` |
| Периодически | **24 часа** | Базовые данные | `f.y = 86400000` |
| Периодически | **7 дней** | Базовые данные + **полный инвентарь приложений** | `f.z = 604800000` |
| Смена SIM | **задержка 6 минут** | Базовые данные (только если ICCID действительно изменился) | `SIMStateReceiver` |
| Изменение сигнала | **при каждом изменении** | RSRP/SINR + местоположение (при `f.e`) | `control.b#onSignalStrengthsChanged` |

**Ключевая деталь:** инвентарь приложений передаётся не каждые 24 часа, а **только раз в 7 дней**. `RegType=S` идёт через `f1.a(ctx,"S")`, который сразу вызывает `new g(...)`; `cVar.K` (AppInfo) равен null, в JSON оказывается `"AppInfo":""`. Только `RegType=A` сначала запускает сборщик `control.e`.

Каждый триггер заново взводит следующий, поэтому цикл самоподдерживающийся:

```java
// ScheduleRegisterReceiver.onReceive
b.c.a.b.a.d(f614a, l.b(context));   // взвести следующий запуск до сбора
...сбор и выгрузка...
```

# Глава 5 — Конфиденциальность: влияние на пользователя

## 5.1 Основное суждение по уровню

Ничто на этом уровне не требует атакующего. Как только телефон загрузился и вставлена SIM-карта, сбор и выгрузка уже начались и продолжаются весь срок службы устройства. Пользователь не знает, что происходит, и не имеет средств это остановить.

> Это не «несколько небрежно реализованных функций». Это **модель сбора, принципиально несовместимая с базовыми основами защиты персональных данных**: она исходит из того, что пользователь не заметит, не откажется и не сможет выйти.

## 5.2 P-01 — Уведомление и согласие существуют лишь формально 【Критическая】

### 5.2.1 Текст уведомления действительно есть

При разборе пула строк `resources.arsc` обнаружены пять фрагментов китайского текста (в DEX **нет ни одного китайского литерала, связанного с конфиденциальностью**):

```
运营商可能通过
或移动数据网络收集您的设备信息等数据
开启即视为同意联网
访问应用列表和定位
运营商服务
```

В восстановленном виде:

> **«Оператор может собирать такие данные, как информация о вашем устройстве, через [Wi-Fi] или мобильную сеть. Включение услуги считается согласием на доступ к сети, доступ к списку приложений и определение местоположения.»**

### 5.2.2 Недостаток первый — раскрытие крайне неполно

| Что должно раскрываться | Есть в тексте? | Что собирается фактически | Разрыв |
|---|---|---|---|
| Информация об устройстве | Да, в общих словах | Модель, прошивка, версия аппаратуры | Приемлемо |
| Список приложений | Да, прямо | **А также время использования и трафик по слотам** | Не раскрыто |
| Местоположение | Да, в общих словах | **CellID/LAC и опционально GPS** | Точность не раскрыта |
| IMEI | Нет | Оба слота | **Не раскрыто** |
| IMSI | Нет | Оба слота | **Не раскрыто** |
| ICCID | Нет | Оба слота | **Не раскрыто** |
| Номер телефона | Нет | Оба слота | **Не раскрыто** |
| Объём ОЗУ / накопителя | Нет | RAM/ROM/FREE | **Не раскрыто** |
| Личность получателя | Нет | `dm.wo.com.cn` (сертификат `O=UNICOM`) | **Не раскрыто** |
| Частота сбора | Нет | 24 ч / 7 дней / загрузка / смена SIM | **Не раскрыто** |
| Срок хранения | Нет | 100 + 500 локальных записей; сервер неизвестен | **Не раскрыто** |
| Передача третьим лицам | Нет | Неизвестно `[C]` | **Не раскрыто** |
| Права пользователя и порядок их реализации | Нет | Канала нет | **Не раскрыто** |

**Полнота: 3 из 13 обязательных пунктов = 23%. По критическим пунктам (получатель / срок / права) полнота — 0%.**

### 5.2.3 Недостаток второй — у текста нет пути отображения

Это самый конкретный и наименее защитимый пункт отчёта:

- **Единственный** собственный интерфейс в APK — `res/layout/activity_test.xml`, чьё содержимое целиком состоит из одного `TextView` с жёстко заданной строкой `"Device Info"`.
- При обходе всех бинарных XML в `res/` **ни один не ссылается на `@string/`**.
- В DEX нет китайских литералов о конфиденциальности.
- В приложении нет ни экрана приветствия, ни диалога, ни экрана настроек, ни раздела «О программе».

```xml
<!-- res/layout/activity_test.xml, целиком (сокращённо) -->
<ScrollView ...>
    <TextView android:id="@+id/tv_device_info"
              android:text="Device Info"/>     <!-- единственный текст, и это заглушка -->
</ScrollView>
```

**Текст — «сиротский» ресурс. В этой сборке нет ни одного пути кода, способного показать его пользователю.**

Статья 17 PIPL устанавливает семь обязанностей по раскрытию. Приложение не выполняет их ни формально, ни по существу. Более того, «текст скомпилирован в APK, но показывать его не стали» при проверке регулятора является **отягчающим**, а не смягчающим обстоятельством: разработчик знал о необходимости раскрытия и решил его не делать.

### 5.2.4 Недостаток третий — форма согласия недействительна

Формулировка «**включение считается согласием**» — классическое **согласие по умолчанию (opt-out)**.

Но IMEI, IMSI, ICCID и номер телефона относятся к **чувствительной персональной информации** по статье 28, а статья 29 требует **отдельного согласия** и возможности пользоваться базовыми функциями после отказа.

Глобальный переключатель в коде:

```java
// b.c.a.b.f
public static boolean g = true;                    // включено по умолчанию

// control.g#run()
if (b.c.a.b.f.g) {
    a(b(this.c));                                  // сбор и выгрузка
    return;
}
b.c.a.b.d dVarA = b.c.a.b.d.a(...);
dVarA.a(this.c.a());                               // даже при отключении данные уходят в локальную очередь
dVarA.close();
j.a("RegisterThread", "User Permission Closed!");  // только запись в лог; данные не отбрасываются
```

Обратите внимание на последние строки: **даже при выключенном переключателе данные по-прежнему записываются в локальную очередь SQLite** — просто не выгружаются сразу.

### 5.2.5 Недостаток четвёртый (уточнённая формулировка) — согласие зависит от модели

Это единственная находка в пользу производителя и место, где первая редакция была слишком категоричной.

## 5.3 P-02 — Сбор выходит за пределы необходимого 【Критическая】

### 5.3.1 Проверка необходимости по полям

В сопоставлении с заявленной целью «регистрация терминала, определение возможностей сети, адаптация VoLTE/5G»:

| Поле | Прямая связь с целью | Способ минимизации | Вывод |
|---|---|---|---|
| `Model` / `Manuf` | Прямая (выбор ветви адаптера) | Нет | Необходимо |
| `OSVersion` | Прямая | Нет | Необходимо |
| `VolteEnabled` / `5GEnabled` | Прямая | Нет | Необходимо |
| `MNC` / `NCLS` | Прямая | Нет | Необходимо |
| `IMEI` | Косвенная (только идентификатор) | Случайный UUID или хеш | Минимизируемо |
| `IPv4` / `IPv6` | Пограничная (диагностика связности) | Использовать и отбросить | Минимизируемо |
| `SignalInfo` (RSRP/SINR) | Пограничная (качество сети) | У оператора уже есть данные OSS | Минимизируемо |
| `ICCID` | Отсутствует | Достаточно индекса слота и оператора | **Избыточно** |
| `IMSI` | Отсутствует | То же | **Избыточно** |
| `MSISDN` | Отсутствует | Номер уже есть у оператора | **Избыточно** |
| `CellID` / `LAC` | **Полностью отсутствует** | Оптимизация сети не требует передачи ID сот с терминала | **Избыточно** |
| `AppInfo[]` | **Полностью отсутствует** | Следует удалить целиком | **Грубо избыточно** |

**Количественно: из 12 категорий 4 необходимых, 3 минимизируемых, 5 избыточных (42%).**

### 5.3.2 Технический аргумент: данных нужно гораздо меньше

Штатный механизм Android Device Owner определяет модель и возможности сети через `Build.MODEL`, `Build.VERSION.SDK_INT` и `TelephonyManager.getNetworkType()` — **без IMEI, без списка приложений, без данных о сотах**.

Спецификации управления терминалами GSMA также построены вокруг «согласования возможностей», а не «сбора идентичности».

Следовательно, «производственная необходимость» не объясняет сбор инвентаря приложений и данных сот — **между этими данными и заявленной целью нет причинной связи, только попутная** `[B]`.

### 5.3.3 Три наиболее интрузивных сбора

**(1) Данные соты позволяют восстановить траекторию**

`CellID + LAC` определяет сектор соты, помещая пользователя в радиус нескольких сотен метров; вместе с `History[]` восстанавливается перемещение во времени. Фактически это **отслеживание местоположения без когда-либо показанного запроса на доступ к геоданным**.

**(2) Инвентарь приложений — это поведенческий профиль**

(`control.e`):

```java
List<ApplicationInfo> installed = pm.getInstalledApplications(0);               // все установленные приложения
List<UsageStats> list = usageStatsManager.queryAndAggregateUsageStats(t0, t1);  // время в foreground по приложениям
NetworkStats ns = networkStatsManager.querySummary(TYPE_MOBILE, imsi, t0, t1);  // трафик по слоту
```

Сериализация одной записи (`b.c.a.b.b#a()`):

```java
jSONObject.put("appLabel", ...);                                  // отображаемое имя
jSONObject.put("pkgName", ...);                                   // имя пакета
jSONObject.put("runTime", this.c + "min");                        // время в foreground
jSONObject.put("tx1", ...); jSONObject.put("rx1", ...);           // трафик SIM 1
jSONObject.put("tx2", ...); jSONObject.put("rx2", ...);           // трафик SIM 2
jSONObject.put("totalData1", ...); jSONObject.put("totalData2", ...);
jSONObject.put("totalDataWiFi", ...);
```

Возможности вывода выходят далеко за пределы «списка приложений»:

| Что выводится | На основании чего | Чувствительность |
|---|---|---|
| Состояние здоровья | Приложения записи к врачу, хронических болезней, фитнеса, трекинга цикла | Здоровье (ст. 28) |
| Религиозные убеждения | Религиозные приложения | Религия (ст. 28) |
| Политические взгляды | Выбор новостных приложений и распределение времени | Конкретная личность |
| Финансовое положение | Набор банковских, кредитных, инвестиционных приложений | Финансовые счета (ст. 28) |
| Социальные связи | Приложения знакомств и социальные сети, часы активности | Личные отношения |
| Несовершеннолетний ли | Образовательные приложения, родительский контроль, детский режим | Несовершеннолетние (ст. 31) |

**(3) Триада идентичности двух SIM полная**

`IMSI + ICCID + MSISDN` вместе — ключевая предпосылка клонирования SIM. Хранение оператором оправдано сверкой с договором; передача по открытому HTTP — нет (см. 6.5).

## 5.4 P-03 — Скрытая выгрузка при загрузке, периодические пробуждения 【Высокая】

### 5.4.1 Хронология

```
t=0        устройство загружается
t≈0        BOOT_COMPLETED (priority=2147483647, раньше почти всех приложений)
t≈0        взводятся три таймера: самозапуск через 4 минуты, 24 ч, 7 дней
t=4min     пробуждение, сбор всех полей, шифрование, HTTP POST
t=24h      периодическая выгрузка (базовые данные)
t=7d       периодическая выгрузка (с полным инвентарём приложений)
также      SIM_STATE_CHANGED (+6 мин), изменения уровня сигнала
```

### 5.4.2 Три намеренных решения

**(1) Максимальный приоритет при загрузке**

```xml
<intent-filter android:priority="2147483647">    <!-- Integer.MAX_VALUE -->
    <action android:name="android.intent.action.BOOT_COMPLETED"/>
    <action android:name="android.intent.action.QUICKBOOT_POWERON"/>
</intent-filter>
```

Гарантирует выполнение как можно раньше — когда пользователь менее всего склонен замечать необычную сетевую активность.

**(2) Задержка на 4 минуты, чтобы обойти пик загрузки**

```java
j.a("OnBootReceiver", " boot delayed for 4 minutes-->");
b.c.a.b.a.b(f611a, 240000L);
```

Запрос в момент загрузки заметен; через четыре минуты система уже спокойна, а трафик и расход батареи трудно атрибутировать.

**(3) Обход Doze**

```java
alarmManager.setExactAndAllowWhileIdle(2, SystemClock.elapsedRealtime() + j, broadcast);
```

`setExactAndAllowWhileIdle` — **единственный тип будильника, способный вывести устройство из глубокого Doze**, и система строго ограничивает его частоту (раз в 9 минут на приложение) именно потому, что он предназначен для критичных по времени задач. Применение его к периодической выгрузке данных противоречит назначению и напрямую увеличивает расход батареи в режиме ожидания.

### 5.4.3 Заметность для пользователя

| Этап | Заметно? | Пояснение |
|---|---|---|
| Сбор | Нет | Ни интерфейса, ни уведомления, ни всплывающего сообщения |
| Выгрузка | Нет | Нет индикатора; при ошибке — скрытый повтор |
| Плановые пробуждения | Нет | Проявляется лишь небольшим ростом расхода в ожидании |
| Первый запуск | Частично | Разрешения на 3 пункта запрашиваются только если пользователь сам откроет `TestActivity`, без объяснения цели |

### 5.4.4 Шесть решений, указывающих в одну сторону

| Решение | Объективный эффект | Обычная практика |
|---|---|---|
| Приоритет загрузки `2147483647` | Опережает почти всё | Обычно не задаётся или 1000 |
| Задержка 4 минуты | Обходит пик загрузки | Причины так делать нет |
| `setExactAndAllowWhileIdle()` | Обходит Doze | `WorkManager`, допускающий пакетирование и откладывание |
| Нет уведомления и иконки | Нет визуального сигнала | Фоновая синхронизация обычно оставляет уведомление |
| Скрытая постановка в очередь при ошибке | Ошибка не показывается | Обычно логируется и показывается |
| Нет экрана настроек вообще | Негде посмотреть или отключить | Обычно есть экран настроек |

**Объективное утверждение:** у каждого из шести есть правдоподобное техническое объяснение (производительность, батарея). Но **все шесть указывают в одну сторону** — снижение вероятности обнаружения. Это верно без вменения мотивов.

## 5.8 P-07 — Принудительно меняет системную настройку VoLTE 【Средняя】

`b.c.a.a.c#a(Context, int)` выполняет запись, формально *читая* состояние VoLTE:


**Реальные последствия для пользователя:**

- VoLTE ускоряет установление соединения, но на некоторых тарифах **видеозвонки могут тарифицироваться отдельно**;
- В международном роуминге тарификация VoLTE отличается от домашней, принудительное включение способно привести к неожиданным списаниям;

Это «сбор данных» как прикрытие для «изменения настроек», что выходит за разумные границы сбора.

### 5.10.1 Проверка шести законных оснований

| Основание (ст. 13 PIPL) | Выполняется? | Причина |
|---|---|---|
| ① Получено согласие | Нет | Действительного согласия нет; см. 5.2 |
| ② Необходимо для договора | Нет | Договор на услуги связи не требует выгрузки полного инвентаря приложений; регистрация устройства возможна по хешу |

## 5.11 Агрегирование данных: по отдельности обычные, вместе — профиль

### 5.11.1 Привязка к личности

```
IMEI (уникален для устройства) + IMSI (уникален для SIM)
+ MSISDN (номер по реальному имени) + ICCID (уникален для карты)
```

Вместе они образуют полный якорь, указывающий на конкретное физическое лицо: устройство, SIM по реальному имени, номер телефона и идентификатор устройства. Оператор уже располагает данными регистрации, поэтому соединение `[C]` превращает все 39 полей в **атрибутированные записи поведения**.

### 5.11.2 Траектория перемещений

`CellID + LAC` даёт от сотен метров до нескольких километров за одно измерение; `History[]` хранит прошлые измерения, и при суточном цикле можно определить:

- место жительства (ночные кластеры сот)
- место работы (дневные кластеры)
- аномальные перемещения (смена сот между городами)
- основную и вторую SIM, а также пересечения границы

При включённом `f.e` добавляется GPS-трек с шагом 1 секунда / 10 метров.

### 5.11.3 Как агрегирование меняет природу данных

| Сочетание | Природа |
|---|---|
| Только `Model` | Статистика устройств, не персональные данные |
| `+ IMEI` | Идентифицируемо устройство, квазиперсональные |
| `+ IMSI + MSISDN` | **Идентифицируется физическое лицо — персональные данные** |
| `+ CellID/LAC + History` | **Отслеживается физическое лицо — чувствительные данные** |
| `+ AppInfo[]` | **Характеризуется физическое лицо — персональный профиль** |
| `+ SignalInfo.location` | **Точно локализуется физическое лицо — чувствительные данные** |

Набор данных, таким образом, переходит порог статьи 24 («автоматизированный анализ, формирующий персональный профиль»), при этом приложение **ничего не раскрывает и не даёт возможности отказаться**.

**Ключевой момент:** даже если сборщик не *собирался* строить профили, **после централизации данных возможность вывода существует объективно**, независимо от намерений. Именно поэтому статья 51 требует деидентификации.

### 5.12.3 Границы

- Отчёт **не вменяет** злой умысел или кражу данных. По коду это компонент управления устройствами, сбор — часть его заявленного назначения.
- Отчёт **не вменяет** нарушение правил регистрации по реальному имени — они требуют от оператора сбора идентификационных данных, а не списка приложений пользователя.
- Отчёт **не вменяет** такое поведение всем предустановленным компонентам. Выводы относятся только к данному образцу.

### 5.12.4 Честная оговорка

«Компоненты управления устройствами собирают IMEI» — в отрасли не редкость; часть аппаратов оператора действительно строит так базу терминалов. Поэтому центральное утверждение здесь — **не «он собирает IMEI»**, а:

> **Собирая значительно больше чувствительных данных, чем необходимо, он не раскрывает информацию действенно, не получает согласия и не даёт возможности выйти.**

Проблема именно в сочетании.

## 5.13 Состав гражданско-правового нарушения

По статье 69 PIPL (презумпция вины):

| Элемент | Установлен | Основание |

## 6.5 S-02 — Открытый HTTP на всём пути 【Критическая】

**CVSS 3.1 (оценка): 7.0** — `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:L/A:N`

### 6.5.1 Доказательство



Нет TLS, нет проверки сертификата, нет пиннинга, нет `network_security_config`.

### 6.5.2 Последствия

- Любой в той же Wi-Fi или на пути оператора получает полный URL и тело запроса.

- Подмена DNS, прозрачные прокси и враждебные точки доступа перенаправляют поток.
- Нарушает обязательное требование статьи 51 PIPL о «шифровании и иных мерах защиты».

### 6.5.3 Устранение

Принудительный HTTPS (TLS 1.2+); удалить `usesCleartextTraffic`; добавить `network_security_config.xml`, запрещающий откат к открытому тексту; закрепить сертификаты для `*.wo.com.cn`.

### 6.6.1 Доказательство

```java
// b.c.a.b.c
public static byte[] a(String s) {                          // (1) MD5(открытый текст)
    return MessageDigest.getInstance("MD5").digest(s.getBytes("UTF-8"));
}

public static byte[] a(String s, byte[] key) {              // (2) AES(открытый текст, key=MD5)
    SecretKeySpec secretKeySpec = new SecretKeySpec(bArr, "AES");
    Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding");
    cipher.init(1, secretKeySpec);
    return cipher.doFinal(str.getBytes("utf-8"));
}

// b.c.a.b.k
Cipher cipher = Cipher.getInstance("RSA/ECB/PKCS1Padding"); // (3) шифрует только MD5
```

### 6.6.2 Шесть дефектов

| № | Дефект | Последствие |
|---|---|---|
| 1 | **Ключ AES = MD5(открытый текст JSON)** | Ключ детерминированно выводится из открытого текста; нет KDF, соли, итераций. Структура JSON предсказуема (фиксированные имена полей, малые домены значений), поэтому перебор офлайн возможен |
| 2 | **Ключ и подпись — одно и то же значение** | `sign = RSA(MD5)`, `key = MD5`. Кто распакует `sign`, получит ключ; одна утечка закрытого ключа компрометирует весь парк |
| 3 | **Режим ECB** | Нет IV; одинаковые блоки открытого текста дают одинаковые блоки шифртекста, что позволяет склейку и анализ повторов |
| 4 | **RSA с PKCS#1 v1.5** | Не OAEP; подвержен атакам класса Bleichenbacher |
| 5 | **MD5 для безопасности** | Коллизии известны; устарел |
| 6 | **Механизм сессионного ключа не реализован** | См. ниже |

### 6.6.3 Шестой дефект показательнее всего

Сигнатура метода выгрузки:

```java
public boolean a(String str, byte[] body, byte[] rsaWrappedSessionKey)
```

Три параметра; третий по смыслу должен быть «случайным сессионным ключом, упакованным RSA». Внутри метода:

```java
OutputStream out = this.f601a.getOutputStream();
out.write(bArr);        // записывается только тело
// bArr2 (третий параметр) не используется ни разу
```

**Схема «случайный ключ + инкапсуляция ключа» была сведена к «выводу из MD5», третий параметр стал мёртвым.** Это не небрежная реализация, а проектирование безопасности, фактически отброшенное в ходе разработки.

### 6.6.4 Проверено экспериментально

Расшифровка тела запроса ключом `MD5(открытый текст)` побайтово воспроизводит исходник (см. приложение D):

```bash
$ openssl enc -d -aes-128-ecb -K $(openssl dgst -md5 plain.json | awk '{print $NF}') \
        -nosalt -in body.bin -out decrypted.json
$ diff plain.json decrypted.json
(вывода нет = файлы идентичны)
```

Это не доказывает «чужой трафик можно взломать», но доказывает главное: **ключ не требует никакого секрета для вывода**. Шифрование даёт обфускацию, а не конфиденциальность.

### 6.6.5 Слабый открытый ключ выгрузки

```
Субъект       : C=CN, ST=BJ, L=BJ, O=UNICOM, OU=UNICOM, CN=UNICOM
Срок действия : 2019-05-24 → 2119-04-30 (100 лет)
Ключ          : RSA 1024 бита
```

NIST SP 800-57 с 2013 года не рекомендует RSA 1024 для новых систем; ротация раз в 100 лет означает, что одна компрометация закрытого ключа действует целый век. Это же объясняет, почему подпись занимает 128 байт, а не 256.

### 6.6.6 Справедливое замечание об ECB

Все 71 блок шифртекста в этом образце уникальны; повторов блоков не наблюдается. Причина — различные значения полей в образце JSON. Теоретические слабости ECB (нет IV, детерминизм, склейка) сохраняются, но **не следует преувеличивать их до «видимых повторяющихся блоков»**.

### 6.6.7 Устранение

Передача по TLS; перейти на `AES-256-GCM` со случайным сессионным ключом через `SecureRandom`, упакованным `RSA-OAEP`; убрать MD5 и ECB; перейти на ключ 2048 бит и сильнее с политикой ротации.

## 6.7 S-04 — Платформенный CA-сертификат + sharedUserId 【Критическая】

### 6.7.1 Доказательство

```
Субъект       : CN=bbkmobile.com.cn, OU=IQOO, O=BBK, C=CN
BasicConstraints: CA:true (PathLen без ограничений)
Срок действия : 2012-09-25 → 2040-02-11 (28 лет)
Алгоритм      : SHA1withRSA / 2048 бит

Манифест      : android:sharedUserId="com.mobiletools.systemhelper.uid"
```

### 6.7.2 Три риска

| Риск | Описание |
|---|---|
| **Ключ подписи является ключом CA** | Повторное использование ключа подписи приложения как ключа CA — антипаттерн; радиус поражения превышает одно приложение |
| **Платформенный ключ широко распространён** | Данные субъекта совпадают с публично циркулирующим платформенным ключом vivo/BBK, многократно перепаковывавшимся в сторонних прошивках |
| **sharedUserId усиливает последствия** | Приложения с той же подписью делят UID и читают приватные каталоги друг друга, включая БД с открытым текстом |

### 6.7.3 Совокупное последствие

При утечке ключа атакующий может подписать APK с «той же подписью», объявив тот же `sharedUserId`, и тем самым:

1. прочитать персональные данные в открытом виде из приватного каталога (600 записей);
2. унаследовать уже выданные runtime-разрешения (включая `READ_PRIVILEGED_PHONE_STATE`);
3. перехватить Binder-канал под тем же UID.

> Примечание: APK содержит блок подписи v2/v3 (`APK Sig Block 42` присутствует), поэтому классическая атака Janus (CVE-2017-13156) **неприменима**.

### 6.7.4 Устранение

Ротировать ключ подписи (собственный для приложения, не CA, SHA-256); пересмотреть необходимость `sharedUserId` (не рекомендуется с Android 10, постепенно ограничивается с 13); шифровать приватные данные, чтобы снизить последствия чтения в пределах одного UID.

## 6.10 S-07 — Слишком широкий набор экспортированных компонентов 【Средняя】

### 6.10.1 TestActivity

```xml
<activity android:name="com.mobiletools.systemhelper.Activity.TestActivity"
          android:exported="true">
    <intent-filter>
        <action android:name="com.mobiletools.systemhelper.activity.testactivity"/>
        <category android:name="android.intent.category.DEFAULT"/>
    </intent-filter>
</activity>
```

- Любое приложение может вызвать его через `startActivity`, что приводит к системным диалогам разрешений — средство **фишинга разрешений**;
- Представление `tv_device_info` показывает полный JSON данных устройства, полученный из `c.b(ctx)`, доступный через скриншоты и сервисы специальных возможностей;
- В имени есть `Test` — забытая отладочная точка входа, которой не место в production.

### 6.10.2 Три экспортированных приёмника

`OnBootReceiver`, `SIMStateReceiver` и `ConnectStateReceiver` экспортированы без разрешений. Хотя `BOOT_COMPLETED`, `CONNECTIVITY_CHANGE` и `SIM_STATE_CHANGED` — защищённые рассылки, которые обычное приложение подделать не может:

- повторное использование `PendingIntent` и комбинации неявных интентов всё же дают пути срабатывания;
- повторные срабатывания вызывают **расход батареи и трафика** (каждое пересоздаёт потоки сбора);
- `SIMStateReceiver` держит статический Context для `unregisterReceiver`, что грозит `IntentReceiverLeaked`.

### 6.10.3 Устранение

Убрать `TestActivity`; установить всем приёмникам `exported="false"` (системные рассылки не требуют экспорта).

# Глава 7 — Почему два уровня усиливают друг друга

Каждый уровень серьёзен сам по себе. Реальная опасность — **мультипликативная**:

| Проблема конфиденциальности | × Уязвимость | = Усиленное последствие |
|---|---|---|
| P-02 собирает личность и поведение по 39 полям | S-01 канал переписывается любым приложением | Любая небольшая утилита собирает подтверждённые личности, местоположение и профили в масштабе |
| P-02 собирает IMEI/IMSI/ICCID | S-02 открытый канал + S-03 выводимый ключ | Данные фактически не защищены в канале |
| P-03 скрытая периодическая выгрузка | S-01 + S-06 удалённое включение логов | Атакующий получает и непрерывный поток, и локальную копию открытым текстом |
| P-06 600 записей открытым текстом | S-04 платформенный ключ + sharedUserId | Подержанное устройство или приложение с тем же UID восстанавливает личность и маршрут прежнего владельца |
| P-05 пользователь не может отключить | S-07 экспортированные компоненты | Пользователь не может отключить сам и не может помешать использовать это другим |
| P-02 инвентарь приложений | S-01 перехват канала | Атакующий может целенаправленно отбирать группы (например, пациентов определённого заболевания) |

**Одной фразой:** первый уровень концентрирует данные, второй заставляет сконцентрированные данные течь неподконтрольно. Вместе они превращают приложение в **терминал сбора чувствительных данных, работающий на устройстве пользователя и управляемый любой третьей стороной**.

DEX требует регистрации каждого вызова в `method_ids`, который ссылается на имена классов в `string_ids`. Поэтому имя класса любого вызванного API обязательно присутствует в `classes.dex` — **если только код не загружает dex динамически или не использует native-библиотеку**. Оба пути проверены и пусты:

| Native-библиотека | количество `.so`, `loadLibrary` | **0 файлов .so, 0 вызовов** |

Дополнительно: `Class.forName` встречается один раз и загружает только `SystemProperties` и варианты `TelephonyManager` — **ни одного класса, связанного с дисплеем или графикой**.

## 8.5 Откуда, вероятно, взялся слух

Три правдоподобных объяснения (предположения, не выводы):

1. **Смешение с другим предустановленным компонентом** — на аппаратах оператора часто есть приложение удалённой поддержки, которое действительно умеет делиться экраном, но это другой APK.
2. **Сбор геоданных принят за «слежку»** — `SignalInfo` действительно содержит координаты, но по природе это сбор местоположения, а не экрана.
3. **`getInstalledApplications` принят за «передачу APK»** — увидев перечисление всех приложений, легко предположить, что передаются и сами APK, тогда как передаются только метаданные.

## 9.2 Ожидаемые возражения и их оценка

| Возражение | Оценка |
|---|---|
| «Это базовое ПО, необходимое для связи» | Частично верно — покрывает 7 полей атрибутов устройства, **но не остальные 32** (инвентарь приложений, данные сот и номера не имеют причинной связи со связью) |
| «Исполняем обязанность по ст. 21 Закона о кибербезопасности» | Не выполняется. Норма требует хранить **сетевые журналы**, а не списки приложений или траектории сот |

## 9.3 Почему уголовный путь сейчас неприменим

Статья 253-1 УК требует «нарушения государственных предписаний путём **продажи или предоставления** персональных данных другим лицам» либо «**незаконного получения**».

Приложение предустановлено оператором на собственные кастомизированные аппараты и передаёт данные на собственный сервер — по коду это сбор и использование для себя, без третьего получателя.

**Однако:** если будет установлена передача третьим лицам или утечка в результате взлома сервера, природа сразу меняется — возможны ст. 253-1 либо ст. 285 (незаконное получение данных компьютерных систем).

# Глава 12 — Заключение

## 12.1 Конфиденциальность

Приложение спроектировано для скрытого, непрерывного и всеохватного сбора. Оно оставило фрагментарный текст уведомления, который никому не показывает, и переключатель согласия, действующий лишь на меньшинстве моделей.

Ноль из десяти законных прав реализовано; ни одно из шести законных оснований не выполняется. Это не «недочёт соответствия» — **сама модель сбора несовместима с основами защиты персональных данных**.

## 12.2 Безопасность

Сервис без защиты и без аутентификации, открытый HTTP-канал, схема шифрования, ключ которой выводится из открытого текста, и платформенный CA-ключ вместе образуют **структурный обвал доверия**. Самый опасный пункт почти ничего не стоит в использовании и контролирует самый чувствительный канал данных.

## 12.3 Связь двух уровней

Это не «небезопасно, поэтому проблема конфиденциальности» и не «слишком много собирает, поэтому небезопасно». **Два дефекта стоят вплотную на одном пути данных**: безграничный сбор в начале, незащищённая передача в конце. Исправление любого одного недостаточно.

## 12.4 О внешнем слухе

«Записывает экран» — не подтверждается. И это не «не нашли», а отсутствие всех четырёх этапов при невозможности обойти статический анализ.

«Передаёт имена пакетов всех APK» — подтверждается. Но интереснее другое: **в приложении есть реальный код сбора GPS, удерживаемый лишь переключателем, выключенным по умолчанию**. Кто может его включить и можно ли включить удалённо — вопрос лучше, чем «записывает ли оно экран».

## 12.5 Рекомендация в одну строку

> Исправить S-01 (0,5 дня), сократить P-02 (5 дней), переписать S-02/S-03 (5 дней) — **менее двух недель работы снимают 80% риска, описанного в этом отчёте**.

## Приложение D — Локальная проверка

Каталог `tools/` содержит замкнутый стенд, который формирует корректный запрос с использованием `assets/pub.cer` и отправляет его локальному макету сервера (никогда на внешний хост).

```powershell
# Терминал 1
python -u capture_server.py 8080

# Терминал 2
bash forge_request.sh sample_valid.json http://127.0.0.1:8080/registerv3
bash ./curl_cmd.sh
```

Макет сервера реализует девять этапов проверки (UA, content type, параметры, длина подписи, выравнивание тела, расшифровка, бизнес-поля, дедупликация, ограничение частоты). Проверены все четыре пути:

| Сценарий | Результат |
|---|---|
| Неверный образец (IMEI не проходит Luhn; несоответствие номера оператору) | `409` |
| Правильный образец | `200` + `regId` |
| Повторная отправка той же подписи (детерминизм RSA) | `416` (клиент считает успехом) |
| Голый curl (без UA Dalvik) | `403` |

**Криптографический вывод подтверждён экспериментально:** расшифровка тела ключом `MD5(открытый текст)` побайтово воспроизводит исходник.

**Вывод по ECB подтверждён экспериментально:** все 71 блок шифртекста в образце уникальны; повторов не наблюдается — не следует преувеличивать до «видимых повторяющихся блоков».
